# Git LFS 사용 가이드

## 1. 목적

이 문서는 Git LFS 설치, 추적 규칙 설정, 파일 추가, 커밋, Push, 검증 및 주의사항만 설명한다.

특정 작업, Issue, 담당자, 기능 또는 실제 데이터 파일에 관한 내용은 포함하지 않는다.

Git LFS(Large File Storage)는 대용량 파일 자체를 일반 Git 객체에 저장하는 대신, Git에는 작은 포인터 파일을 저장하고 실제 파일은 별도의 LFS 스토리지에 저장하는 방식이다.

---

## 2. Git LFS가 필요한 이유

일반 Git은 파일의 모든 변경 이력을 저장한다. 대용량 바이너리나 데이터 파일을 일반 Git으로 반복 커밋하면 다음 문제가 발생할 수 있다.

- 저장소 Clone과 Fetch 속도 저하
- 저장소 전체 용량 증가
- GitHub의 일반 Git 파일 크기 제한 초과
- 삭제 후에도 과거 이력에 파일이 남음
- 팀원 간 불필요한 대용량 데이터 전송
- 저장소 유지·백업 비용 증가

Git LFS는 Git에 포인터만 저장하여 이러한 부담을 줄인다.

> 🚨 **절대 원칙: Git LFS 추적 대상으로 정한 대용량 파일은 일반 Git 객체로 커밋하면 안 된다. 파일을 추가하기 전에 반드시 LFS 추적 규칙이 적용됐는지 확인한다.**

---

## 3. 설치 여부 확인

터미널에서 다음 명령을 실행한다.

```bash
git lfs version
```

정상적으로 설치되어 있으면 버전 정보가 출력된다.

```text
git-lfs/<버전>
```

명령을 찾을 수 없으면 운영체제에 맞게 Git LFS를 설치한다.

---

## 4. Git LFS 설치

## 4.1 macOS

Homebrew 사용:

```bash
brew install git-lfs
```

## 4.2 Ubuntu·Debian

```bash
sudo apt update
sudo apt install git-lfs
```

## 4.3 Windows

Git LFS 공식 설치 프로그램 또는 패키지 관리자를 사용한다.

Winget 사용:

```powershell
winget install GitHub.GitLFS
```

Chocolatey 사용:

```powershell
choco install git-lfs
```

설치 후 버전을 확인한다.

```bash
git lfs version
```

---

## 5. Git LFS 초기화

Git LFS 설치 후 사용자 환경에 초기화한다.

```bash
git lfs install
```

정상 결과 예시:

```text
Git LFS initialized.
```

이 명령은 현재 사용자 환경에서 Git LFS 필터를 사용할 수 있도록 Git 설정을 구성한다.

저장소별 로컬 설정만 사용하려면 다음 명령을 검토할 수 있다.

```bash
git lfs install --local
```

일반적인 팀 환경에서는 사용자 단위 `git lfs install`을 먼저 실행한다.

---

## 6. 추적할 파일 유형 등록

Git LFS로 관리할 파일 패턴을 등록한다.

```bash
git lfs track "<파일-패턴>"
```

확장자 단위 패턴:

```bash
git lfs track "*.확장자"
```

특정 디렉터리의 특정 확장자:

```bash
git lfs track "<디렉터리>/*.확장자"
```

특정 파일:

```bash
git lfs track "<경로>/<파일명>"
```

공백이나 특수문자가 포함된 패턴은 따옴표로 감싼다.

---

## 7. .gitattributes 파일

`git lfs track` 명령을 실행하면 저장소 루트의 `.gitattributes`에 추적 규칙이 추가된다.

형식:

```gitattributes
<파일-패턴> filter=lfs diff=lfs merge=lfs -text
```

각 항목의 의미:

- `filter=lfs`: Git Clean·Smudge 과정에서 LFS 필터 사용
- `diff=lfs`: LFS 파일에 적합한 Diff 처리
- `merge=lfs`: LFS 파일에 적합한 Merge 처리
- `-text`: 일반 텍스트 줄바꿈 변환 비활성화

`.gitattributes`는 개인 환경 파일이 아니라 저장소의 공통 규칙이다. 따라서 반드시 Git에 함께 커밋해야 한다.

```bash
git add .gitattributes
git commit -m "chore: Git LFS 추적 규칙 추가"
```

팀원이 저장소를 Clone하면 `.gitattributes`를 통해 같은 추적 규칙을 적용받는다. 단, 각 팀원의 컴퓨터에도 Git LFS가 설치되어 있어야 한다.

---

## 8. 추적 규칙 확인

현재 등록된 Git LFS 패턴을 확인한다.

```bash
git lfs track
```

특정 파일에 LFS 필터가 적용되는지 확인한다.

```bash
git check-attr filter <파일-경로>
```

정상 결과:

```text
<파일-경로>: filter: lfs
```

다음처럼 출력되면 LFS 추적 규칙이 적용되지 않은 것이다.

```text
<파일-경로>: filter: unspecified
```

파일을 Stage하기 전에 반드시 `filter: lfs` 여부를 확인한다.

---

## 9. LFS 파일 추가와 커밋

올바른 순서:

```bash
# 1. Git LFS 초기화
git lfs install

# 2. 파일 패턴 등록
git lfs track "<파일-패턴>"

# 3. 추적 규칙 커밋
git add .gitattributes
git commit -m "chore: Git LFS 추적 규칙 추가"

# 4. 파일의 LFS 적용 여부 확인
git check-attr filter <파일-경로>

# 5. 파일 추가
git add <파일-경로>

# 6. Stage 결과 확인
git status
git diff --cached

# 7. 커밋
git commit -m "<커밋-메시지>"
```

대용량 파일을 먼저 `git add`한 뒤 나중에 `git lfs track`을 실행하지 않는다. 반드시 추적 규칙을 먼저 등록한다.

---

## 10. Git LFS 포인터 확인

LFS 파일이 Git에 실제 파일이 아니라 포인터로 Stage되었는지 확인할 수 있다.

```bash
git show :<파일-경로>
```

정상적인 LFS 포인터 형식:

```text
version https://git-lfs.github.com/spec/v1
oid sha256:<해시>
size <파일-크기>
```

실제 대용량 파일 내용이 그대로 출력된다면 일반 Git 객체로 Stage되었을 수 있으므로 커밋 전에 중단하고 LFS 설정을 확인한다.

---

## 11. Push

일반 Git Push 명령을 사용한다.

```bash
git push origin <브랜치명>
```

Git은 커밋과 포인터를 Push하고, Git LFS는 실제 대용량 객체를 LFS 스토리지에 업로드한다.

Push 과정에서 다음 형태의 진행 정보가 표시될 수 있다.

```text
Uploading LFS objects: ...
```

LFS 업로드가 실패했다면 일반 Git Push 성공 여부만 보고 완료로 판단하지 않는다. 오류 원인을 해결한 뒤 다시 Push한다.

---

## 12. 커밋 후 검증

현재 저장소에서 LFS로 관리되는 파일을 확인한다.

```bash
git lfs ls-files
```

특정 파일이 목록에 나타나는지 확인한다.

```bash
git lfs ls-files | grep "<파일명>"
```

추적 상태를 자세히 확인한다.

```bash
git lfs status
```

원격 저장소에 필요한 LFS 객체가 모두 업로드됐는지 확인한다.

```bash
git lfs push --dry-run origin <브랜치명>
```

검증 항목:

- `.gitattributes`가 커밋되었는가?
- 대상 파일에 `filter: lfs`가 적용되는가?
- `git lfs ls-files`에 대상 파일이 표시되는가?
- Push 중 LFS 업로드 오류가 없었는가?
- 다른 환경에서 Clone 또는 Pull했을 때 파일을 정상적으로 받을 수 있는가?

---

## 13. 저장소 Clone

Git LFS가 설치된 환경에서 일반 Clone을 실행한다.

```bash
git clone <저장소-URL>
```

Clone 후 LFS 파일이 자동으로 내려받아지지 않았다면 다음을 실행한다.

```bash
git lfs pull
```

LFS 파일 다운로드를 제외하고 Clone하려면:

```bash
GIT_LFS_SKIP_SMUDGE=1 git clone <저장소-URL>
```

이후 필요한 시점에 LFS 파일을 받는다.

```bash
git lfs pull
```

---

## 14. Pull과 Checkout

일반적으로 다음 명령으로 Git 커밋과 LFS 파일을 함께 받는다.

```bash
git pull
```

LFS 객체를 별도로 확인하거나 내려받으려면:

```bash
git lfs fetch
git lfs checkout
```

- `git lfs fetch`: 필요한 LFS 객체를 로컬 LFS 캐시에 가져온다.
- `git lfs checkout`: 포인터 파일 위치에 실제 파일을 배치한다.

---

## 15. 추적 규칙 해제

특정 패턴을 더 이상 Git LFS로 추적하지 않으려면:

```bash
git lfs untrack "<파일-패턴>"
```

변경된 `.gitattributes`를 확인한다.

```bash
git diff .gitattributes
```

변경 내용을 커밋한다.

```bash
git add .gitattributes
git commit -m "chore: Git LFS 추적 규칙 변경"
```

`untrack`은 이후 추가되는 파일에 대한 규칙을 해제하는 것이다. 과거 커밋의 LFS 객체나 이력을 자동으로 일반 Git 객체로 바꾸지 않는다.

---

## 16. 이미 일반 Git으로 커밋한 파일

이미 일반 Git 객체로 커밋된 대용량 파일에 `git lfs track`만 실행해도 과거 이력은 LFS로 전환되지 않는다.

새 커밋부터 LFS로 전환하려면 파일을 Git 인덱스에서 제거한 뒤 다시 추가해야 할 수 있다.

```bash
git rm --cached <파일-경로>
git add <파일-경로>
git commit -m "chore: 파일을 Git LFS 추적으로 전환"
```

이 절차도 과거 커밋의 일반 Git 객체를 제거하지 않는다.

과거 이력 전체를 LFS로 이전하는 명령은 다음과 같다.

```bash
git lfs migrate import --include="<파일-패턴>"
```

> `git lfs migrate import`는 Git 커밋 이력을 다시 작성할 수 있다. 이미 공유된 저장소에서는 팀 전체 승인 없이 실행하면 안 된다.

이력 변경이 필요한 경우:

1. 팀원과 작업 중단 시간을 합의한다.
2. 저장소 백업을 확인한다.
3. 영향을 받는 브랜치와 태그를 확인한다.
4. 마이그레이션 후 모든 팀원이 저장소를 다시 Clone하도록 안내한다.
5. 강제 Push 필요 여부와 보호 브랜치 정책을 확인한다.

---

## 17. 파일 삭제와 용량

현재 브랜치에서 LFS 파일을 삭제해도 과거 커밋과 원격 LFS 스토리지에 객체가 남을 수 있다.

```bash
git rm <파일-경로>
git commit -m "chore: LFS 파일 제거"
git push
```

이 명령은 현재 브랜치에서 파일을 제거하지만 과거 이력의 용량을 즉시 줄이지 않는다.

주의:

- 과거 커밋에서 파일을 계속 참조할 수 있다.
- 원격 LFS 저장 용량이 즉시 감소하지 않을 수 있다.
- 용량 정리는 GitHub 정책과 관리자 권한에 따라 별도 절차가 필요할 수 있다.
- 단순 삭제만으로 LFS 사용량이 복구된다고 가정하지 않는다.

---

## 18. GitHub LFS 제한

GitHub LFS에는 계정·조직·요금제에 따른 저장 용량과 대역폭 제한이 있다.

확인해야 할 항목:

- 단일 파일 크기 제한
- 전체 LFS 저장 용량
- 다운로드 대역폭
- 조직 또는 저장소의 결제 정책
- Fork와 Pull Request에서의 LFS 사용량
- GitHub Actions 또는 CI에서의 LFS 다운로드량

Git LFS는 무제한 외부 스토리지가 아니다. 예상 용량이 크다면 업로드 전에 저장소 관리자와 한도를 확인한다.

한도를 초과할 가능성이 있으면 다음 대안을 검토한다.

- 객체 스토리지
- 데이터셋 전용 저장소
- 아티팩트 저장소
- 릴리스 자산
- 접근 권한이 설정된 외부 파일 저장소

Git 저장소에는 파일 위치, 버전, 체크섬 및 재현 방법만 기록하는 방식도 사용할 수 있다.

---

## 19. 보안 주의사항

Git LFS는 비밀정보 보호 기능이 아니다.

다음 파일은 LFS로도 업로드하면 안 된다.

- API 키
- 액세스 토큰
- 비밀번호
- `.env` 파일
- 인증서와 개인 키
- 개인정보
- 배포해서는 안 되는 원본 데이터

LFS 파일도 저장소 접근 권한을 가진 사용자가 다운로드할 수 있다. 저장소가 공개 저장소라면 LFS 파일도 공개될 수 있다.

민감한 파일을 실수로 Push했다면 단순 삭제만 하지 말고 다음을 수행한다.

1. 관련 키와 토큰을 즉시 폐기한다.
2. 저장소 관리자에게 알린다.
3. Git 및 LFS 이력에 남은 객체를 확인한다.
4. 필요한 경우 GitHub 지원 또는 관리자 절차를 통해 제거한다.

---

## 20. .gitignore와 Git LFS의 차이

`.gitignore`와 Git LFS는 목적이 다르다.

- `.gitignore`: 파일을 Git으로 추적하지 않는다.
- Git LFS: 파일을 Git과 연결해 버전 관리하되 실제 파일을 LFS 스토리지에 저장한다.

파일을 저장소에서 전혀 관리하지 않을 경우 `.gitignore`를 사용한다.

파일을 저장소 버전과 연결해 관리해야 하고 GitHub LFS 한도와 배포 권한을 충족할 경우에만 Git LFS를 사용한다.

같은 파일을 `.gitignore`로 제외하면서 Git LFS로 추적하려 하면 일반적인 `git add`가 동작하지 않을 수 있으므로 관리 정책을 먼저 결정한다.

## 21. 문제 해결

### 21.1 git lfs 명령을 찾을 수 없음

```text
git: 'lfs' is not a git command
```

해결:

1. Git LFS를 설치한다.
2. 터미널을 다시 연다.
3. `git lfs version`을 확인한다.
4. `git lfs install`을 실행한다.

### 21.2 파일이 git lfs ls-files에 나타나지 않음

확인:

```bash
git lfs track
git check-attr filter <파일-경로>
git status
```

추적 규칙이 파일 경로와 일치하는지 확인한다. 파일을 이미 Stage했다면 커밋 전에 Stage를 해제하고 LFS 규칙 적용 후 다시 추가한다.

```bash
git restore --staged <파일-경로>
git add .gitattributes
git add <파일-경로>
```

### 21.3 Push 중 LFS 객체 업로드 실패

확인 항목:

- GitHub 인증 상태
- 네트워크 상태
- GitHub LFS 용량과 대역폭
- 저장소 쓰기 권한
- 원격 저장소 URL

재시도 전 상태 확인:

```bash
git lfs status
git remote -v
```

### 21.4 Clone 후 포인터만 보임

```bash
git lfs install
git lfs pull
git lfs checkout
```

### 21.5 잘못된 패턴을 등록함

```bash
git lfs untrack "<잘못된-패턴>"
git lfs track "<올바른-패턴>"
git add .gitattributes
git commit -m "chore: Git LFS 추적 패턴 수정"
```

## 22. 전체 사용 순서

```bash
# 설치 확인
git lfs version

# 초기화
git lfs install

# 추적 패턴 등록
git lfs track "<파일-패턴>"

# 공통 규칙 커밋
git add .gitattributes
git commit -m "chore: Git LFS 추적 규칙 추가"

# 대상 파일의 LFS 적용 확인
git check-attr filter <파일-경로>

# 파일 추가와 커밋
git add <파일-경로>
git diff --cached
git commit -m "<커밋-메시지>"

# LFS 추적 상태 확인
git lfs ls-files
git lfs status

# Push
git push origin <브랜치명>

# 원격 업로드 상태 확인
git lfs push --dry-run origin <브랜치명>
```

## 23. 최종 체크리스트

- [ ] Git LFS가 설치되어 있다.
- [ ] `git lfs install`을 실행했다.
- [ ] 파일을 추가하기 전에 추적 패턴을 등록했다.
- [ ] `.gitattributes`를 함께 커밋했다.
- [ ] `git check-attr filter <파일>` 결과가 `lfs`다.
- [ ] `git lfs ls-files`에 대상 파일이 표시된다.
- [ ] Push 과정에서 LFS 업로드가 성공했다.
- [ ] 저장 용량과 대역폭 한도를 확인했다.
- [ ] 민감정보가 포함되지 않았다.
- [ ] 일반 Git 이력에 대용량 파일이 먼저 커밋되지 않았다.
- [ ] 이력 변경 명령을 팀 승인 없이 실행하지 않았다.

> 🚨 **최종 확인: 대용량 파일은 일반 Git으로 먼저 커밋한 뒤 LFS로 바꾸는 것이 아니라, LFS 추적 규칙을 먼저 적용하고 검증한 다음 커밋해야 한다.**
